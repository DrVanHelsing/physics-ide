# MakeCode Audit & Block-System Improvement Plan

> Comparison of Microsoft MakeCode's block architecture against Physics IDE's
> current Blockly implementation, plus a prioritized plan to close the gaps.
> Written 2026-05-29. Sources are listed at the bottom.

---

## Part 0 — The two things you asked about

### 0.1 Why the Data Science blocks don't show in the toolbox

**Root cause: the "Data Science" category only exists in the *beginner* toolbox, not the default (advanced) one — and the toolbox is not goal-aware at all.**

There are two hand-written toolbox strings in [BlocklyWorkspace.js](src/components/BlocklyWorkspace.js):

- `TOOLBOX_XML` (the **default / advanced** toolbox) — categories: Starter, Values, Objects, Motion, State, Control, Advanced, Logic, Loops, Math, 3D Math, Text, Lists, Variables, Functions. **There is no Data Science category here at all.**
- `TOOLBOX_BEGINNER_XML` — this one *does* contain the `Data Science` category ([BlocklyWorkspace.js:599-742](src/components/BlocklyWorkspace.js#L599-L742)).

The toolbox is chosen purely by beginner mode at [BlocklyWorkspace.js:1156](src/components/BlocklyWorkspace.js#L1156):

```js
ws.updateToolbox(beginnerMode ? TOOLBOX_BEGINNER_XML : TOOLBOX_XML);
```

So today:

| Project goal | Beginner mode OFF (default) | Beginner mode ON |
|---|---|---|
| physics | physics toolbox | physics beginner toolbox |
| **datascience** | **physics toolbox — no DS blocks** | physics + DS blocks |
| **hybrid** | **physics toolbox — no DS blocks** | physics + DS blocks |

A data-science or hybrid project in the normal (advanced) editor shows the **physics** toolbox and zero DS blocks. The 45 DS blocks are all registered in [blockRegistry.js:262-403](src/utils/blockly/blockRegistry.js#L262-L403) and have working generators in [dsGenerator.js](src/utils/blockly/dsGenerator.js) — they're just not surfaced.

**Two compounding defects:**

1. **DS category is missing from `TOOLBOX_XML`.** It was only ever bolted onto the beginner variant.
2. **The toolbox is not goal-aware.** `BlocklyWorkspace` only receives `beginnerMode`, never `goal` ([BlocklyWorkspace.js:979](src/components/BlocklyWorkspace.js#L979)). A DS project shows Objects / Motion / Scene (irrelevant), and a physics project would show DS blocks if we naively added them to `TOOLBOX_XML`.

**The intended design was never wired up.** The registry already has `getBlocksForGoal()` ([blockRegistry.js:426](src/utils/blockly/blockRegistry.js#L426)) — physics → `{shared, physics}`, datascience → `{shared, datascience}`, hybrid → all. It is fully tested but **only imported by the test file**, never by production. The registry header even says a `buildToolboxXml()` should replace the hand-written XML "in Phase C's DS-block landing" ([blockRegistry.js:13](src/utils/blockly/blockRegistry.js#L13)) — that swap never happened, so the two static XMLs drifted and DS landed in only one of them.

**Fix** → Part 3, P0-1 and P0-2.

### 0.2 No "start of project" anchor for Data Science / hybrid

**Correct — DS and hybrid projects have no equivalent to the physics `sim_start_block` / `sim_end_block`.**

Physics has a real structural anchor:

- `sim_start_block` has a `SETUP` statement input; `sim_end_block` caps the bottom.
- `normalizeSimulationStructure()` ([BlocklyWorkspace.js:877-966](src/components/BlocklyWorkspace.js#L877-L966)) runs on every workspace change and **physically reparents** loose top-level blocks into the start block's `SETUP` input, then forces `sim_end` to the bottom. This is what gives physics the "blocks in use vs. loose blocks" feel.

Data Science has none of this. Code is generated by walking *every* top-level block in spatial order and chaining via `getNextBlock()` ([dsGenerator.js:462-469](src/utils/blockly/dsGenerator.js#L462-L469)):

```js
export function generateDsJsFromWorkspace(workspace) {
  const parts = [];
  for (const top of workspace.getTopBlocks(true)) {  // every top block, ordered by position
    walkChain(top, parts);
  }
  return parts.join("");
}
```

Consequences:
- There is **no visible start**, so a learner can't tell where the analysis "begins."
- There is **no in-use vs. unused distinction** — a stray block you dragged out and forgot still executes, because every top block is collected.
- Execution order is **implicit vertical position**, which is invisible and fragile (nudge a block up by a few pixels and the order changes).

MakeCode solved exactly this problem with **hat/event blocks** + **disabling orphaned blocks** (Part 1.3 and 1.4). That pattern is the recommendation in Part 3, P1-3.

## Part 1 — How MakeCode is built (the reference system)

MakeCode is built on `pxt-blockly`, Microsoft's fork of Blockly — the same engine we use. The differences are in *conventions*, not technology, which is why we can adopt them.

### 1.1 Toolbox = namespaces, with color / icon / weight

Every category is a TypeScript namespace annotated with metadata:

```ts
//% color=190 weight=100 icon="" block="Basic"
namespace basic { }
```

- **color** — a single hue applied to every block in the category (consistency by construction).
- **icon** — a Font Awesome glyph shown on the category row.
- **weight** — sort order; higher floats to the top.
- **block** — friendly display name overriding the namespace.

### 1.2 The "Advanced" drawer

Categories marked `advanced=true` collapse into a single **Advanced** section at the bottom of the toolbox, hidden until the user expands it. micro:bit's split:

- **Always visible:** Basic, Input, Music, LED, Radio, Loops, Logic, Variables, Math
- **Under "Advanced":** Functions, Arrays, Text, Game, Images, Pins, Serial, Control, Extensions

This is how MakeCode shows ~9 friendly categories to a beginner and ~18 to a power user **from one toolbox definition** — no second hand-written toolbox. (We currently maintain two full XML strings instead, which is the drift that caused bug 0.1.)

### 1.3 Hat / event blocks are the program anchors

MakeCode programs are anchored on **hat blocks** (rounded-top, can't connect above):

- **`on start`** — runs once; setup/initialization.
- **`forever`** — loops continuously.
- **`on button A pressed`, `on shake`, `on radio received`…** — event handlers.

Everything meaningful lives *inside* one of these. This gives a learner an unambiguous "the program starts here," and supports multiple independent entry points (reactive model) rather than one linear script.

### 1.4 Orphaned blocks are disabled (greyed out)

This is the key bit for your question 0.2. From the MakeCode/Blockly mechanism:

> "MakeCode handles orphaned blocks by running through all the top blocks in the workspace and disabling any blocks that aren't in a specific set you want to allow."

Concretely: after each change, MakeCode walks top-level blocks; any block **not** rooted in an allowed hat/event is `setEnabled(false)` → it renders **grey** and **generates no code**. (The same grey treatment also flags duplicate event handlers and un-convertible JavaScript.)

So MakeCode gets "in-use vs. unused" **without physically moving the user's blocks** — gentler and clearer than our physics `normalizeSimulationStructure`, which silently reparents them.

### 1.5 Shadow blocks, dropdowns, wrapped inputs

- **Shadow blocks** fill every parameter with an editable default that can't be deleted — inputs are always valid. *(We already do this well in both toolbox XMLs.)*
- **Enum parameters auto-render as dropdowns**; non-enum dropdowns use a shadow enum block. *(We use field dropdowns / shadows similarly.)*
- Blocks with **4+ parameters auto-switch to external (wrapped) inputs** so they don't grow absurdly wide.

## Part 2 — Side-by-side comparison

| Dimension | MakeCode | Physics IDE today | Gap |
|---|---|---|---|
| Engine | pxt-blockly | Blockly (zelos renderer) | — none, same family |
| Toolbox source | One definition, generated per target | **Two hand-written XML strings** (advanced + beginner) | Drift; DS landed in only one |
| Goal/target awareness | Toolbox built for the active target | **Not goal-aware**; `goal` never reaches the workspace | DS project shows physics blocks |
| Beginner vs advanced | One toolbox + `advanced=true` drawer | Two separate full XMLs maintained by hand | High maintenance, easy to desync |
| Category metadata | color + **icon** + weight, declarative | colors only, in XML | No icons; order is XML position |
| Block registry | Namespace = source of truth | `blockRegistry.js` exists & is the intended source of truth | **Registry not used to build the toolbox** |
| Program anchor | `on start` / `forever` / event **hats** | physics: `sim_start`/`sim_end`; **DS/hybrid: none** | No DS start; no entry point |
| Unused blocks | **Disabled + greyed**, no code | physics: auto-reparented; **DS: all top blocks run** | Stray DS blocks silently execute |
| Execution order | Explicit (inside a hat, top-to-bottom) | DS: **implicit vertical position** of top blocks | Fragile, invisible ordering |
| Shadow defaults | Yes | **Yes** | — at parity |
| Block search | Yes | **Yes** (`BlockSearch`) | — at parity |
| Group labels in flyout | Yes (`group=`) | **Yes** (`<label>`) | — at parity, used unevenly |
| Code ↔ blocks round-trip | JS round-trips; un-convertible → grey block | Python is one-way (blocks → Python) | Bigger effort; later |

**Takeaway:** we're on the same engine and already match MakeCode on shadows, search, and group labels. The real gaps are all **structural**: (a) one goal-aware toolbox generated from the registry, (b) hat-block anchors for DS/hybrid, and (c) disabling orphaned blocks.

## Part 3 — Prioritized recommendations

### P0 — Defects (the answer to "why don't DS blocks show")

**P0-1. Make the toolbox goal-aware.**
Thread `goal` from the manifest → `IDELayout` → `BlocklyWorkspace`. Pick the block set with the `getBlocksForGoal(goal, {beginnerEnabled})` that already exists. A physics project shows physics+shared; a DS project shows DS+shared; hybrid shows everything.

**P0-2. Surface the DS category in the non-beginner editor.**
Minimum fix: add the `Data Science` category to `TOOLBOX_XML` (gated by goal from P0-1 so it doesn't pollute physics projects). Better fix: P1-4 below, which deletes the dual-XML problem entirely.

> P0-1 + P0-2 together are the actual fix for your question. They're small and low-risk: the blocks, generators, and goal logic already exist — only the wiring is missing.

### P1 — Structural parity with MakeCode (high value)

**P1-3. A Data Science "Analysis Start" hat block + disable orphaned blocks.** *(Answers 0.2.)*
- Add `ds_start_block` — a hat-style block ("📊 Start analysis") with a statement input that DS blocks snap under. Optionally `ds_conclusion_block` as the closing cap (you already have `ds_state_conclusion_block` content to reuse).
- Change `generateDsJsFromWorkspace` to collect **only** the chain under `ds_start_block` instead of every top block.
- Adopt MakeCode's **disable-orphans** pass: after each change, grey out (`block.setEnabled(false)`) any DS block not rooted in the start hat. This is gentler than the physics `normalizeSimulationStructure` auto-reparenting and gives the exact "in-use vs. unused" cue you asked for. Consider migrating physics to the same disable approach later for consistency.

**P1-4. Generate the toolbox from the registry (`buildToolboxXml`).**
Build the flyout from `blockRegistry.js` (the planned-but-never-built function referenced at [blockRegistry.js:13](src/utils/blockly/blockRegistry.js#L13)). One source of truth → beginner/advanced becomes a `beginnerVisible` filter (already a field on every entry) and goal becomes a `domain` filter (already a field). **This structurally prevents bug 0.1 from ever recurring** and retires ~340 lines of duplicated hand-written XML. Keep the rich shadow-child defaults by storing them per-entry or in a small defaults map.

**P1-5. Category icons + an "Advanced" drawer.**
Add an `icon` (Font Awesome) and `weight` to each category, and an `advanced` flag, so power-user categories (Advanced, Lists, Text, 3D Math, Functions) collapse under one **Advanced** section — MakeCode's model. This lets one toolbox serve beginners and experts, removing the need for `TOOLBOX_BEGINNER_XML` as a separate document.

### P2 — Polish

- **P2-6. Coherent color palette by domain** — physics in one hue family, DS in another (greens), shared/control neutral. Drive it from the registry so it can't drift.
- **P2-7. Consistent group labels** — every category gets MakeCode-style labeled sub-groups (you already do this in Starter and Data Science; extend to Objects, Math, etc.).
- **P2-8. Reporter-shape consistency for DS** — ensure value-returning DS blocks (mean, count…) use output-connector (reporter) shapes and statement blocks use stack shapes, so shape signals behavior the way MakeCode's do.

### P3 — Later (and behind explicit product-contract triggers)

- **P3-9. Block ↔ code round-trip** — MakeCode preserves un-convertible code as a grey JS block. Our Python path is one-way today; two-way is a large effort and not contract-approved.
- **P3-10. Extensions/packages model** — MakeCode's add-on category system; only relevant if the block set grows much larger.

---

## Suggested sequence

1. **P0-1 + P0-2** — one focused change; DS blocks appear in the right projects. *(Fixes the reported bug.)*
2. **P1-4** — generate the toolbox from the registry; delete the duplicate XML.
3. **P1-5** — fold beginner/advanced into the generated toolbox via `beginnerVisible` + an Advanced drawer.
4. **P1-3** — DS `Analysis Start` hat + disable-orphans. *(Fixes the missing-anchor gap.)*
5. **P2** polish once the structure is in place.

Steps 1–4 are mostly *wiring and consolidation* of code that already exists (registry, `getBlocksForGoal`, DS generators). The only genuinely new authoring is the `ds_start_block` and the disable-orphans pass.
