# Physics IDE — Deep Review & Modernization Proposals (2026-08-19)

Five independent lens audits of the frontend — styling/theming, controls/layout, the Blockly layer, the debug experience, and the 3D viewport — merged into one document. Every claim is cited to `file:line` at the commit on `feature/classroom-platform` (10f8a9d). One caveat carried forward from the viewport lens: the live browser pass could not run (the Chrome bridge was not connected), so viewport rendering claims are derived from CSS/JS rather than screenshots; the two places where a live check is worth doing before acting are flagged inline.

---

## Executive summary

**What's strong.** The architecture is in better shape than the surface suggests. Component-level style discipline is real — inline `style={{}}` is rare, all CSS debt is concentrated in one file, and no test in the 12 test suites selects by className, so class renames and CSS refactors carry near-zero regression risk. The token layer exists and is genuinely semantic: two complete themes with ~60 custom properties (`frontend/src/styles.css:8-208`). The block registry is canonical and CI-enforced (106 entries in `frontend/src/utils/blockly/blockRegistry.js:38-445`, checked by `frontend/scripts/check-block-registry.mjs`). Blockly runs the modern `zelos` renderer (`frontend/src/components/BlocklyWorkspace.js:335`) with a custom `dialogService` replacing `window.prompt` (`BlocklyWorkspace.js:301-317`) and ~115 of 122 blocks carrying real tooltips. The debug checkpoint machinery — regex-injected trace points polled from the parent — is cleverer than it looks. The newer platform screens already share primitives across domains by accident (`frontend/src/components/classes/ClassChrome.js:28,55,60,27,48,77` borrows `admin-btn`, `admin-tabs`, `auth-error`, `auth-brand`, `auth-text`), which means an implicit shared component set already exists and only needs promoting, not inventing.

**What's dated.** Three things, in order of how much they cost.

1. *The token layer stops at color.* There are no spacing tokens and no type scale: 216 `font-size` declarations across 17 distinct pixel values including `9.5px` and `11.5px`, ~117 `border-radius` declarations of which only 11 use `var(--radius)`. Four unrelated color palettes coexist — the VS Code token set, a hardcoded Tailwind-400 family through the debug/trace region with *no light-theme overrides at all*, 16 Blockly category hues locked inside an XML template string (`frontend/src/utils/blockly/toolbox.js:45-416`), and a pastel Tailwind-300 set on the landing page (`frontend/src/welcome/GravityPlayground.js:4`). This, more than color choice, is why the screens feel like different apps.

2. *Advertised features that do not work.* Every keyboard shortcut the IDE promises is fiction — `Toolbar.js:195` ("Ctrl+Enter"), `:341` ("Ctrl+S"), `:371` ("Ctrl+C"), documented again at `HelpPage.js:488,1972` — while the only `keydown` listeners in the repo are `DebugMode.js:177` and `HelpPage.js:241`. Breakpoints can be set on any block (`BlocklyWorkspace.js:528-539`) but only seven block types emit a checkpoint that can pause (`blocklyGenerator.js:1924-1927`). Pause flips the React state immediately whether or not the runtime actually stopped (`DebugMode.js:207-215` vs `glowRunner.js:498-503`). 19 of 106 block-search results dead-end silently. The viewport screenshot export almost certainly produces a blank rectangle while reporting success (`useExport.js:110-135`).

3. *The IDE core has no primary action, no focus states, and no first-run guidance.* Run is a transparent green text link at the same visual weight as Reset and Clear (`styles.css:344-351`), while every newer screen has exactly one filled accent primary (`.auth-submit`, `styles.css:4234`). There are zero `:focus-visible` rules in 4,494 lines. The viewport's only instruction to a new student — "Press Run to start the simulation" — renders at `opacity: 0.18` (`styles.css:912`), roughly 1.15:1 contrast. A blank Blockly canvas says nothing at all.

**The three biggest wins.**

1. **A one-week token-and-primitive sweep.** Map the rogue Tailwind palette onto the existing semantic tokens, add a global `:focus-visible` ring, add spacing/type/radius tokens and adopt them in the ~340 lines of new platform screens, and extract `.btn` / `.card` / `.panel-header` / `.input` primitives from the components that already exist. This is mostly mechanical, fixes light-mode contrast failures for free, and is the single highest visual-consistency-per-line-changed change available.

2. **Make the first ten minutes legible.** Fix the invisible viewport idle state, give the blank block canvas a real empty state with starter chips, surface the eight templates on the start-menu landing instead of three clicks deep, implement the keyboard shortcuts the UI already promises, and promote Run to a filled primary. None of these are hard; together they change what a student sees on day one.

3. **Make the debugger and the toolbox tell the truth.** Non-firing breakpoints, a Pause that lies, errors that never render in Debug Mode, blocks that ship in templates but exist in no drawer, and search results that dead-end are all correctness bugs wearing UI clothing. Fixing them costs less than building anything new and removes the "this tool is broken" conclusion a student currently reaches on their own.

## Styling & Theming

### Today

The entire frontend is styled by one 4,494-line global stylesheet (`frontend/src/styles.css`, imported once at `frontend/src/index.js:4`) with ~730 class selectors and 88 `!important` declarations. Two complete themes are defined as ~60 semantic custom properties (`styles.css:8-119` dark, `:122-208` light). Three structural cracks sit in that token layer: a "compatibility alias" block (`:104-116`, mirrored `:193-205`) gives every concept a second name; two rival card families exist with *different values* (`--bg-card: rgba(255,255,255,0.04)` at `:18` vs `--card-bg: rgba(255,255,255,0.025)` at `:71`); and the tokens cover color only.

The premise that the newer platform screens define the current visual language does not survive inspection — they are measurably *less* token-disciplined than the IDE core they postdate. `.start-card` (`:2049`) uses `var(--radius-lg)`, `var(--card-bg)`, `var(--card-border)`, `var(--transition)` and a hover shadow; `.class-card` (`:4352`) hardcodes `6px`, uses the solid `var(--border)` instead of the alpha card border, and has no transition at all. `.vdialog-input:focus` (`:3015`) does the right thing with a `box-shadow` ring; the newer `.auth-input:focus` (`:4205`) regressed to a bare `outline`. The new screens were written thin and fast.

## Controls & Layouts

### Today

A faithful VS Code Dark+ pastiche: a fake window titlebar (`IDELayout.js:338-343`), a flat 38px toolbar of 14+ text-link buttons (`Toolbar.js:167-397`), a two-pane flex split with a 5px drag divider, and a saturated `#007acc` status bar (`styles.css:16`, `1770-1781`). It is internally coherent but chrome-heavy: titlebar (30px) + toolbar (38px) + pane header (35px) = 103px of furniture before a block is visible, and three of those surfaces say the same thing — "Block Editor" appears at `IDELayout.js:341`, `:398`, and as "Mode: Blocks" at `:503`. ## Block Toolbox & Blocks

### Today

Architecturally decent, visually a decade behind. One master toolbox (`toolbox.js:42-418`) filtered per goal by `buildToolboxXml(goal)`, backed by the CI-enforced 106-entry registry. The renderer is `zelos` — the right call. But block colors are 12 raw Blockly hue integers hardcoded across 115 `colour:` lines in `blocklyGenerator.js`, rendered through `Blockly.Themes.Classic` with no `blockStyles` (`BlocklyWorkspace.js:98`), producing muddy 2016-era fills like `#a6805b`. Toolbox *category* colors are a separate set of 16 hex values drawn from three unrelated palettes, and only Logic and Math match the blocks inside their own drawer — and only because both were left at stock defaults.

Beginner mode is a ghost: `beginnerVisible` is set on all 106 registry entries and `getBlocksForGoal` filters on it (`blockRegistry.js:467-478`), but `buildToolboxXml` ignores it and `beginnerEnabled` is persisted, schema-validated (`manifest/schema.js:96,120`) and read by nobody.

## Debug Experience

### Today

## Suggested modernization roadmap

Three tranches, sized for planning rather than estimation. Each is independently shippable and leaves the product better than it found it.

### Tranche 1 — Visual foundation (~1 week)

*Goal: one visual language, correct in both themes, with no behaviour changes to review.*

- Token layer: spacing ramp, type scale, three formalised radii; deprecate then delete the alias block (`styles.css:104-116`, `193-205`); collapse the two card families.
- Global `:focus-visible` ring and `--focus-ring` token.
- Rogue-palette sweep → semantic tokens across the debug/trace region and the DataPanel regression readouts; welcome-page white-alpha fixes; global scrollbar treatment.
- Extract `.btn`, `.card`, `.input`, `.tabs`, `.alert`, `.panel-header` primitives from the components that already exist; rename by role with one release of aliases.
- Adopt the new tokens across the ~340 lines of platform screens (`styles.css:4158-4494`) and lift the debug panels to platform scale (6px radii, 12-13px body, 36-40px headers).
- Viewport idle state, `--text-muted` → `--text-dim` on pane headers and the controls hint, `.dm-glowhost` background parity, Blockly `isDark` at inject, `.tb-label`, Blockly font-size 11 → 13.
- Dead-code deletions and the documentation corrections from Quick wins 16 and 18.

**Questions to settle before starting.** (a) `--radius` moves from 4px to 6px — this is deliberate modernization and changes the look of every existing surface; confirm. (b) Do the 2px coloured pane-header stripes go, or are they house identity worth keeping? (c) Self-hosting Inter and JetBrains Mono adds ~200KB of build assets to `frontend/public/fonts` but no npm dependency — approve or defer? All other items in this tranche are plain CSS/JS with no dependency implications.

### Tranche 2 — Interaction upgrades (~2 weeks)

*Goal: the controls do what they say, survive a reload, and work on a Chromebook.*

- `useHotkeys` in IDELayout, with kbd chips on Run and a corrected Help shortcuts table.
- Merged 44px header: brand, click-to-rename project title, three action zones, account chip routing to `/classes` and `/profile`; quiet status bar carrying project · save state · run status.
- Two-stage responsive toolbar collapse with an overflow menu; split moved from inline style to a CSS custom property so the stacking breakpoint works; pointer events on all three drag handles plus a `pointer: coarse` target-size bump; `.admin-table` scroll container and one platform breakpoint.
- Layout persistence via the existing `useLocalStorage`; `showStart` derived from the restored `activeProjectId`.
- Guest-aware `SyncChip` plus an explicit Save.
- Empty and loading states: Blockly ghost overlay with starter chips (a home for `BeginnerGuide`), templates surfaced on the start-menu landing, a `booting` phase between Run and first frame, a `WelcomeGate` spinner.
- One `<Overlay>` wrapper across the four dialogs; `dialogService.alert` replacing the raw `alert()`; a persistent inline error banner.
- Viewport camera cluster (reset / fit / fullscreen / screenshot), ResizeObserver + devicePixelRatio, live theme sync into the iframe, and the screenshot-capture fix.
- Blockly: search inserts the block, wheel-zoom/slider sync plus "Fit to blocks", Advanced-drawer chevron, `sim_start` pre-placed in blank projects.

**Questions to settle.** (a) The toolbar restructure invalidates most of the 45 checked-in `e2e/*.png` — approve a single screenshot-refresh commit at the end of the tranche rather than churning them mid-series. (b) There are no component tests; a thin render-and-click suite per toolbar control group should land *before* the restructure, which is a small scope addition. (c) The screenshot fix and ChartOverlay fix use the already-installed `html2canvas`, so no new dependency. (d) Everything here is plain JS — no state library, no CSS framework.

### Tranche 3 — Deeper mechanics (~3-4 weeks)

*Goal: the block palette becomes part of the design system, and the debugger stops lying.*

- `BLOCK_PALETTE` module as the single source for category *and* block colour, mirrored as `--cat-*` custom properties so pane-header accents, help-page tags and start-menu badges can align; contrast raised so every fill clears AA; `sim_end` and the debug highlights repointed off red.
- Toolbox integrity: DS split into pipeline sub-categories, the three template-shipped blocks added to Objects, the five phantom registry entries deleted, and `check-block-registry.mjs` extended to validate category names and toolbox membership in both directions.
- Connection type checks on the vector and dataframe chains; unified orphan handling (grey, don't adopt) matching `docs/product-contract.md:36`; `helpUrl` on every block; one label voice encoded in the registry.
- Debug as a mode, not a world: revive `.debug-drawer` as a docked TraceTable beside the normal viewport, fold the step/record group into the existing toolbar, retire the parallel `.dm-ctrl-*` vocabulary.
- Debugger truthfulness: breakable-id publishing with legible non-breakable markers, pause acknowledgement from the runtime, breakpoints seeded before `eval`, setup/constants instrumentation plus watch expressions, "Next frame" stepping with an iteration readout, `describeRunError`, trace-table value legibility.
- Blockly `componentStyles` read from live CSS tokens; scene `title`/`caption` surfaced in React chrome; CSS split into `@import`ed local files.

**Questions to settle — these are the dependency-approval items.** (a) **Bundling Blockly.** `frontend/index.html:15-19` loads Blockly from `cdn.jsdelivr.net` at a floating `@11` with no SRI hash, and `blockly` is absent from `frontend/package.json`. This means a Blockly patch release can change block rendering in a classroom mid-term with no review, and a filtered school network renders the headline feature inert. Fixing it means `npm i blockly@11.x` pinned exactly — a genuine new dependency needing sign-off. (b) **Vendoring GlowScript.** `glowRunner.js:22-31` pulls six scripts from `glowscript.org`, a single non-hardened origin; every debug improvement above is bounded by it, and `docs/product-contract.md:101` promises the app "runs fully offline after first load". Self-hosting is the prerequisite for the debugger ever being reliable in a school, and is exactly the kind of infrastructure the standing deferral preference says to push behind an explicit trigger — so raise it as a decision, not a task. (c) **Monaco** (`index.html:22`, `CodeEditor.js:39-47`) has the same exposure, with a bare `<textarea>` fallback at `CodeEditor.js:156-165`. (d) Everything else in this tranche stays plain JS with new logic written as pure helpers under `utils/`, matching the existing utils-only test policy.

## Open questions for the product owner

1. **Which half sets the visual direction?** The audit assumption was that the newer platform screens define the current language, but they are measurably less disciplined than the IDE core they postdate (`.class-card` vs `.start-card`; `.auth-input:focus` vs `.vdialog-input:focus`). Do we lift the platform screens to the IDE's rigour, calm the IDE toward the platform's softness, or meet in a new middle? Tranche 1 assumes the third.
2. **Is the VS Code costume still the goal?** The fake titlebar, the `#007acc` status bar and the uppercase letterspaced pane headers are a deliberate 2024-era pastiche. Retiring them makes the product read as contemporary and matches the classroom screens; keeping them preserves a professional-tool signal for older students. This decision gates the merged-header work in Tranche 2.
3. **Do we accept a new npm dependency to fix offline?** Bundling Blockly (and eventually GlowScript and Monaco) is the only path to the offline/local-first behaviour `docs/product-contract.md:101` already promises, and it removes three third-party origins from the classroom threat model. It also directly contradicts the standing "no new deps / defer infrastructure" preference. This is the single largest open decision in the review.
4. **Should the block palette change at all?** Category identity is legitimately hue-coded and students learn it. The contrast fixes are non-negotiable for a classroom sale (10 of 12 hues fail AA today), but the *hues themselves* could stay recognisable or be re-designed wholesale. Which?
5. **Debug Mode: separate world or mode of the shell?** Re-homing it retires ~25 duplicate CSS rules and lets students edit-and-step without a context switch, but it is the largest single item in the review and changes a workflow teachers may already have built lessons around.
6. **Beginner mode: delete or ship?** ~106 lines of registry metadata, a manifest field and a schema rule exist for a feature nothing consumes. Walkthrough Mode is on the roadmap (`docs/product-contract.md:92`) — is this its foundation, or dead weight to remove now?
7. **What is the minimum supported viewport?** The IDE core's fixed three-pane layout is a defensible desktop-only choice; the classroom screens have zero responsive handling and are the ones most likely to open on a Chromebook or tablet. Naming a floor (1024px? 768px?) sizes the responsive work precisely.
8. **Is touch a supported input class?** Every divider in the product is mouse-only and toolbar targets are ~20px. Pointer events are a cheap mechanical fix, but "usable on a tablet" is a larger commitment than "does not break on a tablet".
9. **How much e2e screenshot churn is acceptable?** The 45 checked-in PNGs in `e2e/` are documentation as much as tests; the Tranche 2 header work invalidates most of them, and several are already stale.
10. **Is the missing component-test layer worth building now?** No test covers Toolbar, IDELayout or StartMenu, so a control restructure can ship broken with CI green. A thin suite is a small scope addition to Tranche 2 — but it is scope that produces no user-visible value.
11. **What should Ctrl+S mean?** Students expect save. It is currently advertised as export (`Toolbar.js:341`), implemented as nothing, and intercepted by the browser. Save is the right answer, but it changes the meaning of a documented shortcut.
12. **Do the templates' scene captions matter?** `precodedExamples.js` authors explanatory `scene.title`/`scene.caption` text that is currently clipped out of view. Reviving it in React chrome is a small feature; deleting the strings is smaller. Which was the intent?
