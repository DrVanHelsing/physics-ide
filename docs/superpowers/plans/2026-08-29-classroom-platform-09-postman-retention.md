# The Postman, the Port, and the Retention Clock — Plan 9 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The spec's last step delivered: real email through a provider driver behind the existing one-seam `Mailer` (spec §9's "only the postman does [change]"), the §10 Health promises made true (bounce status, storage used), DEPLOY.md's pre-GCP checklist discharged in code, §11's retention proposal turned into admin-adjustable machinery riding the daily tick, and the GCP port prepared to the exact boundary of the user's hands — Dockerfile, runbook, secrets map — with the provisioning session itself explicitly user-gated, last.

**Architecture:** One new driver (`createBrevoMailer` — provider HTTP API via Node 20 `fetch`, ZERO new dependencies) selected by explicit `MAIL_DRIVER` config, never NODE_ENV magic; the dev pretend inbox stays a true preview of the real article (it is load-bearing test infrastructure — ~20 token-regex assertions across 11 suites and both e2e scripts confirm through it). One webhook route updates `emails.status` by provider message-id. Retention = `classes.archivedAt` + a settings row + a sweep in its OWN advisory-locked transaction ahead of the tick's reminder scan, deleting the class and letting the FK cascade carry its records. The port = `infra/` + `docs/DEPLOY-GCP.md`; provisioning is the one stage that stops for the user.

**Spec:** `docs/superpowers/specs/2026-08-29-classroom-platform-09-postman-retention-design.md` (cite as **D§n**) over `docs/classroom-platform.md` §9/§10/§11/§15.10 and `docs/classroom-platform-stack.md` + `DEPLOY.md` (the accepted constraints). ## Global Constraints

- **The Mailer interface does not change** (D§3): `MailMessage = { to, toUserId?, template, subject, text }`, `send(): Promise<void>`. Drivers own their persistence; the provider message-id never crosses the seam.
- **The wrapper order is fixed and load-bearing** (D§4): `neverThrow(app.log, withPreferences(deps.db, suppressErased(driver)))`. Never-throw is OUTERMOST because no send site has a try/catch — anything outside it can still reject into thirteen handlers, including `withPreferences`' own `notification_prefs` SELECT. No task re-derives this order; Task 2 pins it with a test.
- **Dev/test email behavior is byte-identical to today, in the sense the suites actually depend on:** no change to token URLs and no change to the persisted-body shape the token regexes read (`token=([A-Za-z0-9_-]+)`). `createDevMailer` is untouched; every existing suite runs the dev driver exactly as before; the pretend inbox keeps full clickable bodies under `MAIL_DRIVER=dev` (the default). Any task that breaks a token-regex assertion in an existing suite has broken this constraint — fix the task, not the suite. (The two deliberate body changes — the /profile footer line on the five switchable templates, and `marksReleased` dropping the score and the comment — both land in `templates.ts` for BOTH drivers, because spec §9 promises the pretend inbox shows the mail "exactly as it would look". Neither touches a token-bearing template.)
- **No queues, no background workers, no retry machinery, ever** (stack §3/§7). A failed send is a visible row, not a scheduled retry. One 10-second `AbortSignal.timeout` is the send's whole budget.
- **The events ledger is untouchable** — no index, no column, no deletes. Retention deletes CLASSES (the FK cascade carries their records), the class's `notifications`, and `emails` rows by age; `events` rows are never deleted, and the sweep writes its own events. READING the ledger is permitted and Task 8's backfill does exactly that, once.
- **Every mutation's event in the same transaction; refusal sentences as file-level consts asserted verbatim; zod on every multi-field body; matrix arithmetic re-derived in the same task that moves it** (the house rules, unchanged). The arithmetic moves TWICE in this plan: Task 4 (a named skip) and Task 8 (a row).
- **Truth in copy:** the real-email NON_CLAIMS group and the pretend-inbox copy move ONLY in Task 14a, after real mail has genuinely flowed to the maintainer's own address and BEFORE any send to a third party — not when the driver merely exists. The retention copy on /privacy changes in the same task its sweep ships (Task 9). Contract amendment first (Task 1), contract-before-code.
- **Secrets never land in the repo**; `.env.example` documents names only. The runbook maps each secret to Secret Manager.
- **Postgres runbook** (unchanged): after any `schema.ts` edit run `npm run db:generate -w backend` then root `npm run db:migrate` (dev AND test DBs). Drizzle names the migration file; a data statement may be APPENDED to it after a `--> statement-breakpoint` (this repo's migrations are plain SQL and already use breakpoints), but the DDL drizzle generated is never hand-rewritten.
- **ESLint stays green at every commit** (`npm run lint`).

1. **The wrapper composition order is load-bearing, and never-throw is OUTERMOST** (T2): `neverThrow(log, withPreferences(db, suppressErased(driver)))`. A reviewer re-derives it from one fact — no send site has a try/catch — so anything outside never-throw can still reject into thirteen handlers, `withPreferences`' pref SELECT included. The earlier "preferences outermost so a switched-off send is never counted a failure" reasoning was vacuous: a switched-off send returns normally under any order and `neverThrow` counts nothing.
2. **Dev-driver fidelity is the plan's spine, and "byte-identical" is scoped** — the suites depend on token URLs and the persisted-body shape the token regexes read, not on every byte. Three protections: `MAIL_DRIVER` defaults `dev`; the footer lands in `templates.ts` so the pretend inbox stays a TRUE preview (spec §9's "exactly as it would look") rather than diverging from the real article; every existing suite runs unmodified. T3's reviewer verifies no token-path diff.
3. **The forgot throttle counts `email_tokens` JOINED to `users` on the address, filtered to `type = 'reset'`** (T5) — the table has no email column and both flows share it, so a bare count would let a stranger's signup consume a reset budget. Unknown addresses mint no row at all and lean on the existing per-IP limit; the 200 body is identical in all three cases.
4. **Two unrelated `sent` fields, two different tasks.** The tick's `{ sent }` (T9) has exactly one consumer, `tick.test.ts` — grep `res.json()` there. `invites.ts`'s `{ sent }` is a separate lie with its own consumers (`invites.test.ts` ×4 and `PeopleTab.js:58`) and is renamed to `invited` in T2, the commit that makes it false. A blanket "grep every `{ sent` consumer" collides the two.
5. **The retention sweep is a cascade, plus two things the cascade cannot reach, minus one thing it must not touch** (T9). Cascade: everything keyed on `classes.id` goes with `DELETE FROM classes`. Explicit: the class's `notifications` (no FK to classes; a denormalised `classId` payload) and `emails` by age. Untouched: every `projects` row, group-linked included — D§10 fiat 11, because the erase route's precedent spares the group workspace, because the founding member is LIVE and local-first sync would push the project straight back, and because individual assignment work was always kept. The plan's earlier "group-linked projects GO" ruling was wrong on all three counts and would have left /privacy promising a deletion that undoes itself while every test stayed green.
6. **T12's bounce-in-browser has no fallback branch, because the tree already answered.** Only a driver writes `emails` rows, the dev driver sets no `providerId`, and no admin route creates one — so the e2e drives the tab and the two webhook refusal/drop contracts, and the `bounced` render is T4's unit test. The script's comment says why.
